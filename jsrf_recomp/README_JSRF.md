## What the analysis says about JSRF

- **Clean API-level title.** None of the game code talks to the NV2A or APU
  directly. Every GPU and audio access goes through D3D8 / DirectSound calls the
  runtime already replaces. The `in`/`out` and `0xFDxxxxxx` hits in `.text` are
  data decoded as code and bitmask immediates, not hardware access.
- **Rendering:** 102 D3D8 entry points used (97 named). Heaviest users are
  `SetRenderState_Simple` (61 call sites), `SetVertexShaderConstant` (29), and
  `SetTextureState_BumpEnv` (15). Programmable vertex shaders and pixel
  shaders (`CreatePixelShader`) are both used, so expect the register-combiner
  path to matter for the cel-shading look.
- **Audio:** 52 DSOUND entry points, including `DownloadEffectsImage` and
  `Set/GetEffectData` (50 call sites). JSRF drives the APU's DSP effects
  directly (the `DOLBY` section is DSP microcode), so audio will be the
  harder half.
- **MMATRIX** is Smilebit's own SSE matrix library (40 functions, 4,137 call
  sites). It's game code and recompiles as-is.
- **No overlays:** every code section is preloaded, so `XeLoadSection` is only
  bookkeeping.
- **Known toolkit history:** the xboxrecomp changelog has JSRF-specific fixes
  (`frndint` rounding breaking animation tables, ADPCM header validation
  silencing ~4% of audio). Stay on a toolkit version at or after those fixes.

## Known loose ends

- **Fixed after run 1:** 10 C++ static constructors in the `__xc_a` table
  (`0x1EB760`) weren't detected as functions, so their ICALLs failed and they
  never ran. `analysis/seeds.json` now seeds them, plus 57 other code pointers
  found in `.rdata`/`.data` and `GetSpeakerConfig`. Total is now 8,771 functions.
- **Open: D3D runs LLE.** The XDK's own D3D library (`CMiniport_InitHardware`,
  `CDevice_InitializeFrameBuffers`) is programming the NV2A directly, but the
  runtime only provides zeroed GPU registers. The D3D8 entry points need to be
  intercepted and routed to `xbox_d3d8`.
- **Fixed after run 4: heap corruption.** Write-watch showed `operator delete` freeing a block already on the free list. `tools/difftest` proved the XAPI heap lifts correctly, so the culprit was the 183 do-nothing stubs for undetected functions, one of them an `AddRef` (`0x3A900: inc [ecx+0x10]; ret`). 69 of them are now seeded; 113 stubs remain, mostly targets of false calls decoded from data.
- **Added after run 5: heap checker** (`src/recomp_manual.c`). It wraps RtlAllocateHeap / RtlFreeHeap / RtlReAllocateHeap (`0x1497DC` / `0x149F5E` / `0x14A12E`), tracks live blocks, and reports then skips any free or realloc of a pointer that isn't live. Lines start with `[HEAPCHK]`. `RECOMP_HEAPCHK=0` disables it. It needs the lift run with `--exclude-manual` (below).
- **Fixed after run 6:** 4 worker-thread entry points (`0x13B180/1C0/230/2A0`), 2 XAPI USB driver callbacks (`0x1BD274`, `0x1BCAA3`) and 20 other callbacks referenced only as data or immediates are now seeded. Run 6 showed the threads starting and exiting without running any code.
- **Run 6 finding:** the bad frees all come from teardown after the top-level `Init` (`sub_0005F2C0` → `[vtbl+0x18]`) fails. The `0xFFFFFFFF` crash is in that teardown, so the init failure is the thing to chase.
- **Fixed after run 7: split functions.** Every remaining stub was reached by a *jump*: a branch into code the detector had put in another function's body, or in none (e.g. `0x154D70`'s `case 1` at `0x154DAA` was skipped every call). All real-code targets are now seeded; the disassembler turns ones inside a function into alias entries (a separate copy to the owner's end, owner untouched). `tools/seed_stub_targets.py` does this and is iterated until it adds nothing (4 rounds here).
- **Run 8 finding:** no stubs reached and no crash. The bad frees all happen inside `0x15FCC0`, which creates the input interface (`[0x251D64]`), while it unwinds a failed create. Most likely the cause is no USB hardware: `run_jsrf.bat` now enables `RECOMP_USB`, `RECOMP_USB_PADS=1` and `RECOMP_KEYBOARD`. The heap checker now also says whether a bad free is a double free, an interior pointer or a use-after-free, and which code allocated or freed the block.
- **Run 9 finding:** every bad free is a back-to-back double free: the input object's vector buffer pointer equals the object itself. - **v117 (CPU headroom: texture checks and draw submission):**
  - *Write-watch instead of hashing.* Textures and render targets in the contiguous window are protected read-only once checked. The first write to a page, from any thread and through either the window or the tiled alias, faults once; a handler unprotects that page and counts it. A check is then answered without reading the bytes: nothing written since its mark, so no hash and no upload. Only a range with a written page is hashed, as before. A texture is now checked at every bind (decals rewritten mid-frame are caught exactly) at no cost. Textures whose pages are written frame after frame (sharing pages with other data) go back to the old once-a-frame hash for 10 s at a time.
  - Kernel-side writes cannot fault into the handler, so `NtReadFile` unprotects and pins its buffer around the `ReadFile`. A pinned page is never protected. Surface read-backs unprotect their range in one call rather than faulting page by page.
  - `RECOMP_GL_TEX_WATCH=0` turns the watch off.
  - The 512-entry texture lookup has a direct-mapped hint first.
  - *Rings.* Vertex and index data go into persistently mapped, coherent buffers (ARB_buffer_storage): one memcpy per draw instead of two `glBufferSubData` calls. Each ring is split into 8 segments with a fence each. Leaving a segment fences it and entering one waits for its fence, which the GPU has passed long before (a ring holds about 15 frames). `RECOMP_GL_PERSIST=0` restores `glBufferSubData`.
  - *Vertex-program constants.* Each of c[0..191] records when it last changed, and a program is sent only the range changed since it last ran, usually a matrix or two instead of all 192 (3 KB) per draw. The program's live size of `u_c[]` and the consecutive locations are checked at link. `RECOMP_GL_FULL_CONSTS=1` sends all of them.
  - New `[PERF]   submit:` line: checks answered by the watch / hashed, watched pages written, protects, constant vectors per draw, ring waits. The `of which` line splits out "batch setup (indices, state)".
  - Tests: the GL scenes are identical to the v105 references at 1x, with the rings on and off. With the same program and two constants changed between three draws, partial and full uploads give identical output. A ring stress test (1M random allocations, a lagging GPU) never overwrites data a pending draw reads. ## Re-running the lift (e.g. after adding seeds)

`analysis/functions_named.json` holds the named function list. From the
xboxrecomp clone:

```bat
copy jsrf_recomp\game\default.xbe game_files\
py -3 -m tools.xbe_parser game_files\default.xbe --json game_files\default_analysis.json
py -3 -m tools.disasm game_files\default.xbe --force --seed-functions ..\jsrf_recomp\analysis\seeds.json
py -3 -m tools.func_id game_files\default.xbe
py -3 -m tools.abi_analysis game_files\default.xbe
:: re-apply XDK names (or copy analysis\functions_named.json over tools\disasm\output\functions.json)
py -3 -m tools.recomp game_files\default.xbe --all --split 250 --game-name "Jet Set Radio Future" --gen-dir ..\jsrf_recomp\src\recomp\gen --exclude-manual ..\jsrf_recomp\src\recomp_manual.c
py -3 ..\jsrf_recomp\tools\apply_xdk_names.py ..\jsrf_recomp\analysis\xbsymboldb_symbols.txt tools\disasm\output\functions.json   :: before the recomp line
py -3 ..\jsrf_recomp\tools\log_stubs.py ..\jsrf_recomp\src\recomp\gen\recomp_stubs_unresolved.c
```

## Files in `analysis/`

- `xbe_inventory.txt`: header, certificate, sections, XDK libs, kernel imports
- `game_to_xdk_calls.txt`: every D3D/DSOUND/XPP function the game calls, with call counts
- `xbsymboldb_symbols.txt`: raw XbSymbolDatabase output (functions and globals such as `D3D_g_pDevice`)
- `functions_named.json`, `abi_functions.json`, `identified_functions.json`: pipeline databases
- `recomp.log`: lifter output
